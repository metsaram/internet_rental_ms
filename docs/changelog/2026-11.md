# Changelog — November 2026

## [2026-11-04]
### Added
- **Prisma PostgreSQL Lateral Join Strategy (elationLoadStrategy: "join")** — Enabled `previewFeatures = ["relationJoins"]` in `prisma/schema.prisma` and applied `relationLoadStrategy: "join"` across heavy relational queries:
  - **Single Query Execution**: Replaced N+1 sequential `SELECT` queries (6 separate network queries for contracts + nested service, branch, shop, provider, plan, user) with a single PostgreSQL query utilizing `LEFT JOIN LATERAL` and `JSONB_BUILD_OBJECT`.
  - **Measured Performance Gains**: Decreased cold `GET /api/contracts` execution from 5,509 ms down to 1,192 ms (78.4% latency reduction). Warm response times dropped from ~3,172 ms to ~1,064 ms.
  - **Applied Endpoints**: `src/app/api/contracts/route.ts`, `src/app/api/invoices/route.ts`, `src/app/api/services/route.ts`, and `src/app/api/dashboard/route.ts`.
- **API Read Parallelization (Promise.all)** — Parallelized independent database queries to eliminate sequential round-trip wait times:
  - **Contracts API (src/app/api/contracts/route.ts)**: Concurrently fetches `internetContract.findMany` and `company.findUnique` for `warningDays`.
  - **Notifications API (src/app/api/notifications/route.ts)**: Concurrently fetches `notification.findMany` and `notification.count`.
- **TanStack Query Frontend Cache Tuning (src/components/providers.tsx)** — Enhanced cache policy to eliminate redundant background round-trips:
  - Increased `staleTime` from 30s to 60s, keeping view switches fresh without refetching.
  - Set `gcTime` to 5 minutes (300,000 ms), preserving inactive route query data in memory for instant back-navigation.
  - Added `refetchOnReconnect: true` to guarantee fresh data after network reconnects.
- **Performance Optimization Plan (docs/performance/performance_optimization_plan_2026-11-04.md)** — Documented the revised 4-phase optimization roadmap incorporating PgBouncer verification, lateral join benchmarking, query parallelization, and deferred region migration strategy.
- **Verification Suites**: Created `test/contracts-route-get.test.ts` (7 tests) and `test/notifications-route-get.test.ts` (9 tests) verifying parallel execution, default parameter fallbacks, and response serialization (all 32 test files, 294 tests passed).

### Fixed
- **HTML Hydration Mismatch in DetailGrid (src/components/views/invoices.tsx, src/components/views/shops.tsx)** — Resolved Next.js React hydration error (In HTML, <div> cannot be a descendant of <p>):
  - Updated `DetailGrid` in `invoices.tsx` and `shops.tsx` to render row values inside a `<div className="text-sm">` container instead of a `<p>` tag.
  - Replaced `<div key="...">` wrappers for Branch, Shop, and Provider detail entries in `InvoiceDetailSheet` with semantic inline-block phrasing elements (`<span key="..." className="block">`).
## [2026-11-03]
### Added
- **Global Database Singleton Pool & Connection Capping (`src/lib/db.ts`)** — Enforced database connection management standards across all Next.js API routes and server actions:
  - **Singleton Pool on `globalThis`**: Replaced isolated development-only caching with unconditional global caching of the extended Prisma client (`globalThis.prismaExtendedClient` and `globalThis.prisma`), eliminating redundant `$extends` evaluations and preventing multiple client instantiations across separate bundles in production.
  - **Connection Limit & Pool Timeout Capping**: Implemented `getCappedDatabaseUrl()` to dynamically inspect and enforce `connection_limit=10` (or configurable via `DB_MAX_CONNECTIONS`) and `pool_timeout=30`, preventing PostgreSQL connection exhaustion under heavy concurrent traffic.
  - **Environment-Aware Logging**: Restricted SQL query logging to development mode (`NODE_ENV === "development"`), eliminating high-traffic I/O bottlenecks in production.
  - **Comprehensive Verification**: Added `test/db-singleton.test.ts` verifying connection URL parameter injection, custom limit overrides, and singleton global assignment (all 30 test files, 278 tests passed).
- **Database Performance & Latency Investigation Report (`docs/performance/database_latency_analysis_2026-11-03.md`)** — Documented live benchmarks identifying root causes of multi-second response times for small result sets (frontend mapping takes only 1.05 ms vs ~5s Supabase network/PgBouncer latency to Sydney, AU). Outlined migration and parallelization remedies.

### Fixed
- **Invoice Alert Modal & Notification Generation Warning Days Synchronization** — Fixed invoice payment alerts displaying invoices due in ~30 days when company "Days Before Warning" setting is set to 7 days:
  - **Server-side Notification Cleanup (`src/lib/notifications.ts`)**: Updated `generateNotifications` so when an invoice is outside the alert window (`!alert`, due in > `warningDays` or overdue past `-warningDays`), any lingering unread payment reminder is deleted. Added cleanup for orphaned notifications from deleted invoices and upcoming renewal alerts farther than `warningDays`.
  - **Company Setting Update & Cache Invalidation (`src/app/api/company/route.ts`, `src/app/api/notifications/route.ts`, `src/components/views/settings.tsx`)**: `PATCH /api/company` now clears the notification generation throttle and immediately regenerates notifications when `warningDays` changes. `SettingsView.save()` invalidates `["notifications"]` and `["notifications-unread-count"]`.
  - **Modal & AppShell Dynamic Filtering (`src/components/shared/invoice-alert-modal.tsx`, `src/components/app-shell.tsx`)**: Introduced `parseInvoiceAlertDays` utility to extract days from titles and messages. `InvoiceAlertModal` and `AppShell` now accept and enforce `warningDays={companyWarningDays}`, filtering out any stale notifications exceeding the threshold.
  - **Test Suite Verification**: Added tests in `test/invoice-alert-modal.test.tsx` for `parseInvoiceAlertDays` and warningDays modal filtering (all 29 test files, 272 tests passed).
