## Task: Fix Invoice Alert Dialog Respecting Company Warning Days Setting

### User Request
"Check the dailog @[d:\Projects\internet_rental_ms\src\components\shared\invoice-alert-modal.tsx] I sett alert in 7 days in company setting, but current it get alert for invoice in 30days too."

### Root Cause Analysis
1. **Flawed Cleanup Check in `generateNotifications` (`src/lib/notifications.ts`)**:
   - When a company is created or initialized with default settings, `Company.warningDays` is 30.
   - While `warningDays` was 30, `generateNotifications` evaluated invoices due within 30 days (such as `INV-2026-4170` due in 27 days on 2026-11-27) and generated an unread notification (`type: "INVOICE_DUE_SOON"`).
   - When the user later reduced the company's "Days Before Warning" setting to 7 days, subsequent notification generation calls properly evaluated `getInvoicePaymentAlert(inv, outstanding, now, 7)` as `null` (since 27 days > 7 days).
   - However, the cleanup logic inside `if (!alert)` was:
     ```ts
     const isPastLimit = due ? Math.round(...) < -warningDays : false;
     if (inv.status === "VOID" || outstanding.lte(0) || isPastLimit) {
       await db.notification.deleteMany(...);
     }
     ```
     This check only verified whether the invoice was past the overdue limit (`< -warningDays`), VOID, or paid. It completely neglected checking whether the invoice was in the future beyond `warningDays` (`daysToDue > warningDays`).
   - Consequently, unread notifications for invoices due in ~30 days were never cleaned up from the `notifications` database table.

2. **Absence of Trigger & Cache Invalidation on Company Setting Update**:
   - `PATCH /api/company` did not trigger notification regeneration or clear the 60-second generation throttle when `warningDays` was changed.
   - `SettingsView` (`src/components/views/settings.tsx`) invalidated `["company"]`, `["dashboard"]`, `["invoices"]`, `["renewals"]`, `["contracts"]`, but omitted `["notifications"]` and `["notifications-unread-count"]`.

3. **Missing Client-Side Threshold Guard in Modal & App Shell**:
   - `InvoiceAlertModal` (`src/components/shared/invoice-alert-modal.tsx`) and `AppShell` (`src/components/app-shell.tsx`) displayed whatever unread notifications were fetched from `/api/notifications?unreadOnly=true` without verifying them against `session.user.companyWarningDays`.

### Implementation Details
1. **Server-side Notification Generation & Invalidation (`src/lib/notifications.ts`, `src/app/api/notifications/route.ts`, `src/app/api/company/route.ts`)**:
   - Updated `if (!alert)` in `generateNotifications` to clean up unread invoice reminders whenever `alert` is null (including when invoices are outside the alert window: `daysToDue > warningDays` or overdue past `-warningDays`).
   - Added automatic dismissal for unread notifications of deleted/orphaned invoices (`entityId: { notIn: invoiceIds }`).
   - Symmetrically cleaned up `RENEWAL_UPCOMING` notifications if a contract's expiration is farther out than `warningDays`.
   - Exported `clearNotificationThrottle(companyId?: string)` in `/api/notifications/route.ts`.
   - Updated `PATCH /api/company` to clear notification throttling and trigger `generateNotifications` immediately upon `warningDays` modification.
   - Cleaned up existing stale notifications in database.

2. **Settings UI Cache Invalidation (`src/components/views/settings.tsx`)**:
   - Added `qc.invalidateQueries({ queryKey: ["notifications"] })` and `qc.invalidateQueries({ queryKey: ["notifications-unread-count"] })` to `save()`.

3. **Client-Side Defense & Modal Filtering (`src/components/shared/invoice-alert-modal.tsx`, `src/components/app-shell.tsx`)**:
   - Added `parseInvoiceAlertDays` utility to extract days from notification title and message formats (`"due in (\d+)d"`, `"(\d+)d overdue"`, `"due today"`, `"due tomorrow"`, etc.).
   - Updated `InvoiceAlertModalProps` to accept `warningDays?: number` and filter out any notification exceeding `warningDays`, returning `null` if no valid alerts remain.
   - Updated `AppShell` to filter `invoiceAlerts` with `companyWarningDays` and forward `warningDays={companyWarningDays}` to `InvoiceAlertModal`.

4. **Automated Verification**:
   - Enhanced `test/invoice-alert-modal.test.tsx` with 4 new tests verifying `parseInvoiceAlertDays` parsing across all title/message formats and `InvoiceAlertModal` filtering out alerts beyond `warningDays=7`.
   - Ran `npx vitest run` across all 29 test files (272 passed).

## Task: Database Connection Singleton & Pool Capping Enforcement

### User Request
"check the current APi setup and foillow this rule:
 Do not create a new database connection inside every API route or Server Action. Under heavy traffic, Next.js will quickly hit PostgreSQL's connection limit and crash. Use a global singleton pool in TypeScript and cap the maximum connections:"

### Audit & Analysis of API Setup
1. **Route Handlers & Server Scope Audit**:
   - Inspected all 25+ route handlers under `src/app/api/**` and domain libraries (`src/lib/**`).
   - Confirmed: No route handler or server action instantiates ad-hoc `new PrismaClient()` or `new Pool()` instances. All route handlers cleanly import `{ db }` from `@/lib/db`.
2. **Singleton Pool Deficiencies in `src/lib/db.ts`**:
   - Previously, `db` was created as `basePrisma.$extends(...)` on every file evaluation rather than caching the extended client itself on `globalThis`.
   - `globalForPrisma.prisma = basePrisma` was only executed when `NODE_ENV !== "production"`. In Next.js standalone and production bundles, multiple chunks in the same process could instantiate separate Prisma clients.
   - `connection_limit` was not enforced programmatically in `DATABASE_URL`, leaving connection pool sizing to CPU defaults (`num_cpus * 2 + 1`), which can exhaust PostgreSQL's connection capacity under heavy traffic.
   - Query logging (`log: ["query"]`) was enabled indiscriminately, causing significant I/O overhead in production.

### Implementation Details
1. **Connection Capping Utility (`src/lib/db.ts`)**:
   - Implemented `getCappedDatabaseUrl()` to inspect `process.env.DATABASE_URL`.
   - Automatically injects `connection_limit=10` (or configurable via `DB_MAX_CONNECTIONS`) and `pool_timeout=30` if absent.
   - Passes the capped connection string to Prisma via `datasources: { db: { url: cappedUrl } }`.
2. **Universal Global Singleton Pool**:
   - Persists the extended client singleton on `globalThis.prismaExtendedClient` and `globalThis.prisma` across both development and production.
   - Prevents duplicate instantiation when Next.js bundles separate route chunks in the same process.
3. **Environment-Aware Query Logging**:
   - Restricted verbose `query` logging to development mode, logging only errors in production.
4. **Test Suite Verification**:
   - Created `test/db-singleton.test.ts` with 6 unit tests covering URL capping, parameter preservation, custom limit overrides, and singleton persistence on `globalThis`.
   - Ran full test suite: all 30 test files (278 tests) passed.
